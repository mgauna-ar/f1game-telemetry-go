# F1 Game Telemetry Project Rules

This file (`.agents/AGENTS.md`) contains workspace-specific rules, architectural boundaries, and operational constraints that agents must strictly follow when working on this project.

## 1. Technology Stack & Architecture
*   **Supported OS:** Windows 10/11, macOS, and Linux (cross-platform).
*   **Target Telemetry Version:** Exclusive target for **F1 2025** and **F1 2026 DLC** UDP telemetry specifications (`PacketFormat` 2025/2026 with fixed 29-byte `PacketHeader`). Deprecated support for 2023 and older formats.
*   **Backend Layer Boundaries (Go):** Standard Go layout (`cmd/` and `internal/`).
    - `internal/api/`: HTTP router, request decoding, middleware, and response serialization only. **Zero heavy domain or analytical logic.**
    - `internal/session/`: Live session tracking, `LapTracker` memory buffering, `TelemetryBatchWriter`, and session import/export services.
    - `internal/analytics/`: Server-side computational analytics (classification standings, lap comparator distance merging, progression matrices, tyre stint degradation OLS regression).
    - `internal/engineer/`: Modular Strategy pattern AI race engineer rules engine (`EngineerEngine`, `EngineerRule`). The engine also keeps the race history (player laps, rival session histories, race events, its own radio calls) and builds the live race picture the AI chat reads (`RaceContext()`, `LiveBriefing()`; served at `GET /api/ai/engineer/race-context`). `internal/ai` reads it through the `ai.LiveRaceSource` interface. `RaceTools()` exposes the race data lookups (`race_tools*.go`) as an `ai.ToolExecutor`.
    - **AI chat context is built on the server:** `POST /api/ai/chat` carries only identifiers in `context` (`ai.ChatContextRequest`: `context_mode` from `ai.ChatContextModes`, plus `session_id` for `session_debrief`, or `lap_a_id`, `lap_b_id` and an optional `zoom` range for `comparator`). `ai.BuildChatContext` builds the prompt data before streaming starts: the live briefing from `ai.LiveRaceSource` (none while telemetry is stale, so the prompt stands by), and the debrief and lap comparison from `ai.RecordedRaceSource`, which `analytics.ChatContextSource` implements (`BuildSessionDebrief` from the classification, `BuildLapComparison` from the merge the Lap Comparator charts use, through the shared `MergeLapComparisonCached`). The API layer adds the saved voice settings' call-sign and custom persona; an unknown session or lap is a 404 and a bad context a 400, both with code `INVALID_REQUEST`. The driving phase, 2026 rules and incident status come only from the engine's briefing, never from text. The browser never writes prompt text or summaries.
    - `internal/storage/`: SQLite repository, data models with custom `MarshalJSON` sanitization, versioned migrations, and raw zstd compression.
    - `internal/packets/`: Strict 1:1 binary UDP telemetry decoders and domain constants.
    - `internal/ai/`: External AI providers (Gemini, OpenAI, Anthropic Claude, and OpenAI-compatible "custom" servers) and neural TTS voice synthesis. `provider.go` is the provider registry: each provider's default model (`DefaultModel()`), which server key it uses (`ServerKeys`), and how to list its models and open a chat. Each provider lives in one file (`gemini.go`, `openai.go`, `claude.go`) and implements `chatSession`: stream one model turn, then append tool results. `chat.go` runs the one shared function calling loop over the `ToolExecutor` in `ChatOptions`: at most `MaxToolRounds` rounds, the last one with function calls disabled, and a retry without tools when a model or OpenAI-compatible server rejects them. Text streams to the client as it arrives in any round, and the stream ends with a single `[DONE]`. Claude goes through the official Go SDK (`github.com/anthropics/anthropic-sdk-go`) with environment defaults off, so it only uses the key the app resolved; Gemini and OpenAI use plain HTTP (`http.go`, `sse.go`). API keys go in headers, never in URLs, and the "custom" provider only uses a key sent with the request.
    - `internal/locales/`: Type-safe `PromptCatalog` interface, thread-safe locale registry, and locale-specific prompt catalogs (`en`, `es`) eliminating boolean language flags in the backend.
    - `internal/input/`: DirectInput PTT wheel and keyboard OS listeners.
*   **Storage Invariants:**
    - CGO-free pure Go SQLite (`modernc.org/sqlite`) with versioned migrations (`schema_version` table).
    - Per-lap telemetry samples buffered in memory and persisted as Zstandard (`zstd`) compressed JSON BLOBs (`lap_telemetry` table) with cascading foreign keys (`ON DELETE CASCADE`).
    - **Settings ownership:** Radio engineer settings (thresholds, alert switches, trigger preset) are owned by the server and persisted in the SQLite `settings` table (`engineer_config`), always loaded on top of `engineer.DefaultEngineerConfig()` so new fields keep their defaults. The UI reads defaults from `GET /api/ai/engineer/config/defaults` instead of hard-coding them. Settings every device shares live in `internal/settings` (one JSON document each in the `settings` table) behind `GET`/`PUT /api/settings/{ai,voice,ptt}`: AI provider, model and API keys per provider (keys are write-only and never returned), the engineer's persona and voice, and push-to-talk (applied to the input manager at startup). AI requests are completed in the API layer in the order request, saved setting, env var (`GEMINI_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `LLM_PROVIDER`, `LLM_MODEL`), built-in default, and `internal/ai` owns the default model names. Only per-device preferences (volume, radio effects, alerts on/off, view modes, the AI chat's expanded size) live in `localStorage`, through `frontend/src/utils/storage.ts`, with every key listed in its `KnownStorageKey` type. The router rejects cross-site writes (`http.CrossOriginProtection`) and sends no CORS headers. The WebSocket upgrader keeps gorilla's default origin check, so `/ws` and `/ws/engineer` only accept handshakes whose `Origin` host equals the request `Host` (the dashboard by localhost or LAN address, or the Vite dev proxy) or that send no `Origin` (non-browser clients); never override `CheckOrigin`. JSON request bodies on `/api` are capped at `MaxJSONBodyBytes` (2 MB); `POST /api/sessions/import` sits outside that group with its own `MaxImportPayloadSize` (100 MB). The update check always queries `system.DefaultGitHubRepo`. Server startup settings come from flags, then environment variables, then an optional `.env` file.
    - **Session UIDs must always be stored and serialized as Hex strings** (`TEXT` e.g. `0x...`) to prevent 64-bit signed integer overflow and JavaScript float truncation.
*   **Single-Binary Release & Frontend Distribution:** Compiled Vite frontend (`frontend/dist`) is embedded directly into the Go executable via `//go:embed` (`frontend/embed.go`), serving static assets with SPA fallback and automatic browser launch (`system.OpenBrowser`). Produces a 100% self-contained binary with zero external runtime dependencies.
*   **Communication & Performance:** `/ws` carries one message type: the throttled 10Hz consolidated Live Telemetry Snapshot (`PacketIDLiveSnapshot` 255), and the frontend store ignores anything else. The snapshot is a slim DTO (`session.LiveSnapshot` in `internal/session/live_snapshot.go`), not the raw packets: one row per active car (`ActiveCarCount`, which keeps a retired car's slot), only the packet fields the live views read (same PascalCase names and types as the packet structs), only the filled weather forecast samples, and no marshal zones. The store copies the rows as they are. The engineer engine and session recording keep reading the raw packets. `TestLiveSnapshotPayloadSize` (`cmd/simulator`, run with `-v`) measures a simulator frame against the raw packet snapshot for both formats. **The server owns the race-control feed:** `LiveBroadcaster` turns the game's events (Packet ID 3) and the rows it builds from session and lap data (pit entry, penalty counter, retirement, DSQ, safety car) into one `session.FeedEvent` shape (`internal/session/feed_events.go`: an event code from `FeedEventCodes`, a feed type and severity, and typed parameters such as vehicle indices, driver names, penalty type and time, lap, speed and safety-car status; never text, and an unnamed car gets no name), queues them, and sends them in the next snapshot's `Events`. The store only appends them (`useSessionStatusStore.addEvent`); `frontend/src/utils/raceEvents.ts` writes every row's text and tag in `en` and `es`, with a switch `tsc` checks against the generated `FeedEventCode` union. Both sockets are ref-counted singletons built on `createSharedSocket(path)` in `frontend/src/utils/websocketClient.ts` (`connectTelemetryWebSocket`, and `subscribeEngineerMessages` in `frontend/src/utils/engineerSocket.ts`): the first subscriber's URL wins, and handler exceptions are logged with `console.error`. `/ws/engineer` consumers never cast frames: they pass one handler per message type to `subscribeEngineerMessages`, and `dispatchEngineerMessage` drops anything that isn't a known `EngineerSocketMessage` type. On the Go side the API layer sends its messages only through `Server.broadcastEngineer`, which takes the typed PTT messages; the engine broadcasts its `EngineerDirective`s itself. React frontend uses decoupled Zustand stores (`useTelemetryStore`) with fine-grained selectors to eliminate unnecessary whole-page re-renders. The AI race engineer context is split in three (`context/RaceEngineerContextDefinitions.ts`): `useRaceEngineerActions()` holds only callbacks that never change identity (`useAIChatStream` and `useAIModels` read the latest messages, settings and chat target through refs), `useRaceEngineerState()` holds the chat window, context mode, chat targets (`ComparatorChatTarget`, `SessionDebriefChatTarget`: IDs plus a track name for the badge) and AI settings, and `useRaceEngineerStream()` the messages. The app shell and the pages only use the actions, so nothing re-renders on a timer or per streamed chunk (`App.rerender.test.tsx`); `utils/chatContext.ts` turns the mode and targets into the request's `context`. Streaming SSE for AI Race Engineer (`/api/ai/chat`) follows one contract on both sides: the server (`internal/ai/sse.go`) sends `data: {"text":…}` chunks and a final `data: [DONE]`; a provider failure after streaming starts is sent as one last `data: {"error","code","provider","message"}` frame on the 200 response (built by `aiErrorPayload` in `internal/api/ai.go`), and a request rejected before streaming gets a non-OK JSON response with the same fields (bad request bodies use code `INVALID_REQUEST`). The frontend reads it only through `frontend/src/utils/sseUtils.ts`: `readChatStream(res, onText)` (reads `text`, does not require `[DONE]`, throws a typed `ChatStreamError` with the server's `code` on an error frame) and `chatStreamErrorFromResponse(res)` for non-OK responses; both the chat panel (`useAIChatStream`) and push-to-talk radio (`useRadioAudio`) use them. Error codes come from the server (`classifyAIError` in `internal/ai/errors.go`); the client only labels requests that never got an answer as `NETWORK_ERROR`. Model lists from `POST /api/ai/models` are already filtered to chat models by the server. Chat replies are parsed by `frontend/src/utils/chatMarkdown.ts` (headings, nested lists, tables, code, quotes; unfinished blocks stay text while streaming) and rendered as React elements by `components/ai_engineer/ChatMarkdown.tsx`, never as raw HTML. The AI settings panel (`ChatSettingsDrawer`) shows one card per provider and only that provider's fields; OpenAI-compatible server presets live in `AI_SERVER_PRESETS` (`constants/f1.ts`).
*   **Wire Types (Go → TypeScript):** The frontend's types for server JSON are generated from the Go structs by `cmd/tsgen` into `frontend/src/types/generated/` (one file per Go package; never edit them, never hand-copy a wire type). `cmd/tsgen/main.go` is the registry of root types: the REST responses (sessions, laps, participants, tags, the session detail with its classification, progression and stints, comparator, import, settings, engineer config, system, AI models and errors), the AI chat request (`ai.AIChatRequest`, with the `ChatContextMode` union built from `ai.ChatContextModes`), the `/ws/engineer` messages (`EngineerSocketMessage` = `EngineerDirective` | `PTTEventMessage` | `PTTLearnedMessage` | `PTTLearnTimeoutMessage`, with the directive's `EngineerAlertKey`, `EngineerDirectiveCategory` and `EngineerUrgency` unions built from `engineer.RadioAlertKeys`, `DirectiveCategories` and `Urgencies`) and the race feed (`session.FeedEvent`, plus the `FeedEventCode`, `FeedEventType` and `FeedSeverity` unions built from the Go lists in `internal/session/feed_events.go`). The generator (`internal/tsgen`, standard library only) follows the `encoding/json` rules; a field whose JSON differs from its Go type carries a `tstype:"…"` tag, rows of a `[]map[string]any` are described with `TypeAlias`, and a type with its own `MarshalJSON` must be registered with `Marshaler` (a sample value plus the type describing its JSON; `TestMarshalerKeys` checks one against the other). Responses are named structs, never `map[string]any`. Hand-written files re-export the generated types (`types/session.ts`, `types/settings.ts`, `types/telemetry.ts`, …); where the UI narrows a Go `string` to a union it uses `Narrows<T, Base>` (`types/wire.ts`), so `tsc` still checks it against Go. Tests build complete wire objects with the factories in `frontend/src/test/wireFactories.ts`. The 10 Hz live snapshot is registered as `session.LiveSnapshot`; `types/telemetry.ts` re-exports its rows under the names the components use (`LapData`, `CarStatusData`, `CarDamageData`, `CarTelemetryData`, `CarTelemetry2Data`, `ParticipantData`, and `SessionData` = `LiveSession` plus the header's `PacketFormat` and `SessionUID`), and tests build them with the `makeLive*` factories.
*   **REST Errors:** Non-OK REST responses carry `{"error","code"}` (`internal/api/response.go`). The frontend calls REST only through `frontend/src/utils/apiClient.ts`: every method (JSON, form data, blob, array buffer) goes through one `request()`, and `parseErrorResponse()` turns the body's `error` text into `ApiError.message`, which toasts show as is; `api.stream()` alone returns the raw `Response` for `sseUtils.ts`. A failed `POST /api/sessions/import` (400) sends the import summary with `error` set to the first `details[].reason`. Batch export is `POST /api/sessions/export-batch` with a JSON `{"session_ids":[…]}` body only.
*   **Session Detail & Session Data Cache:** Session History opens a session with one request, `GET /api/sessions/{id}/detail` (`analytics.SessionDetailResponse`, built by `analytics.ComputeSessionDetail` from one load of the session, participants and laps). Participants and laps are sent once, at the top level; `DriverStanding` and `DriverStint` never embed laps or participants (their Go fields that do are `json:"-"`), and the client joins them by `car_index` and `best_lap_id` in `normalizeDriverStanding` (`types/session.ts`). The participants and laps of a session go through `frontend/src/utils/sessionDataCache.ts`: `useSessionDetail` primes it, and the comparator (`useSlotTelemetry`) reads it with `getSessionLapData`, which shares one `/participants` + `/laps` load per session between both slots and keeps at most `SESSION_DATA_CACHE_LIMIT` sessions. Deleting sessions drops them from the cache and importing clears it. `TestSessionViewPayloadSize` (`internal/api`, run with `-v`) checks that a session view sends each lap once and reads the database once, and prints the bytes.
*   **Live Status & Telemetry Endpoint in the UI:** Only the Live tab opens the telemetry WebSocket. The live feed state (offline / listening / live / stale, stale after 3s without packets) comes from `useLiveStatus()` and drives the nav badge, the live header and the tab title; never show "LIVE" just because the backend is reachable. The UDP port and this PC's addresses come from `GET /api/system/network` (`system.DescribeTelemetryEndpoint`, loaded into `useTelemetryEndpointStore`); never hard-code port 20777 in the UI.
 
## 2. Testing Standards & Quality Verification
*   **Mandatory Pre-Completion Verification Rule:** NEVER declare any task, refactor, or feature complete without first executing and verifying all linters, test suites, and production build:
    1. **Go Backend Linters & Formatting:** Run `gofmt -l .`, `go vet ./...`, and `golangci-lint run` (verify 0 formatting issues, 0 vet errors, 0 linter issues).
    2. **Generated Wire Types:** Run `go run ./cmd/tsgen -check` (0 stale files; regenerate with `go run ./cmd/tsgen` after changing a Go wire type). `go test ./...` also fails when they are stale (`TestGeneratedFilesUpToDate`).
    3. **Go Backend Tests:** Run `go test -count=1 ./...` from the workspace root (ensure 100% pass across all packages without relying on test cache). Always use table-driven tests for packet parsers and proper error handling.
    4. **React Frontend Linters:** Run `npm run lint` (`oxlint`) in `frontend/` (ensure 0 errors).
    5. **React Frontend Tests:** Run `npm test` (`vitest run`) in `frontend/` (ensure 100% pass across all test suites).
    6. **Production Build:** Run `npm run build` in `frontend/` (`tsc -b && vite build`) to verify zero TypeScript compiler errors and bundle integrity.
    7. Always report actual test pass counts, linter output, and execution results in the final user response.
*   **Packet Simulation:** Use `make simulate` (defaults to F1 2026 24-car grid, or `make simulate FORMAT=2025` for 22-car grid) or `simulate.bat` (`cmd/simulator/main.go -format 2026/2025`) to generate synthetic live UDP telemetry packets (Motion, Telemetry, LapData, ParticipantsData, CarDamage, Event, Session with weather forecasts) at 20Hz without needing the physical F1 game. Use `-scenario <name>` flag to trigger specific in-race situations for testing the Voice Race Engineer: `wear` (tyres start at 38.5% → fires tyre deg alerts), `sc` (Full Safety Car), `vsc` (Virtual Safety Car), `rain` (rain forecast injection), `start` (formation lap thermal prep, grid alignment, and launch reaction debrief), `pit` (pit limiter engagement, penalty hold, stationary stop duration debrief, and limiter exit release).
*   **Windows Helpers:** `run.bat` automated setup script (installs frontend deps if missing, builds production assets, compiles and launches the standalone single-binary embedded application, auto-opens browser). `simulate.bat` shortcut for UDP simulator.
*   **React Frontend:** Use `vitest` and `@testing-library/react` (`jsdom`) for component and hook testing (like the `useTelemetry` hook).

## 3. F1 Telemetry & Radio Protocols
*   **Binary Parsing Alignment:** When modifying packet decoding logic (e.g. `PacketLapData`, `PacketMotionData`), ensure strict 1:1 alignment with official EA F1 2025/2026 game telemetry specification. **Critical gotcha:** `LapDistance` and `TotalDistance` are floats positioned immediately before `SafetyCarDelta`.
*   **Lightweight Payloads:** Keep frontend payloads lightweight — broadcast only the specific data points needed by the UI (e.g. extracting `WorldPositionX/Z` for track maps) rather than sending raw, unparsed packets. A live view that needs another packet field adds it to the matching `Live*` struct in `internal/session/live_snapshot.go` (and its `toLive*` converter), then regenerates the wire types; never send a whole packet struct.
*   **Proactive Radio Protocol:**
    - **The dashboard owns the spoken wording of proactive calls.** A directive on `/ws/engineer` carries its alert key (`sub_alert`, one of `engineer.RadioAlertKeys`), category and urgency, and no text; `Title` and `Message` stay on the server for the log and the AI race history. The dashboard maps the key to a phrase category (`frontend/src/constants/radioAlertCategories.ts`, a `Record<EngineerAlertKey, RadioAlertCategory>` that `tsc` checks) and speaks a random phrase for the persona from `locales/{en,es}/radio_phrases.ts` (`getProactiveRadioSpeech`; Bono and Colapinto fall back to the standard pool, custom always uses it). Never guess a category from text, and never read the engine's text out. A new alert needs its key in `RadioAlertKeys` (`TestRadioAlertKeys_MatchWhatTheEngineEmits` checks it against the rules), a category in `radioAlertCategories.ts`, and phrases in both catalogs; F1 2026 variants are their own keys (e.g. `rival_attack_override`).
    - All proactive pit wall alerts are prefixed with `[PROACTIVE PIT WALL CALL]`.
    - **Explicitly forbid "Entendido" / "Copy" / "Roger" on proactive calls** since the engineer initiates the communication.
    - "Entendido" / "Copy" / "Roger" are **only** permitted when the driver spoke first via Push-to-Talk (PTT).
    - **Direct 2nd Person Radio Voice:** Directives must instruct the driver directly in 2nd person (e.g., *"Box now, box box!"*, *"Introduce Lift & Coast into Turn 1"*), never 3rd person directives (*"Order driver to..."*).
    - **Phase Lifecycle Discipline:** Strict radio discipline per session phase (`DrivingPhase`):
      - `PhaseFlyingLap`: Strictly silence non-critical coaching, fuel delta, ERS low, tyre wear, and rival chatter. Only lap invalidations and critical emergencies (`UrgencyCritical`) may transmit.
      - `PhaseGrid` & `PhaseRaceStart`: Absolute radio silence during countdown and Lap 1 start sequence, permitting only critical safety car or terminal damage calls.
      - `PhaseInGarage` & `PhasePitLane`: Only strategic session alerts (clock countdown, radar, red flags) adapted for garage/pit lane; no driving coaching or on-track tyre alerts. Silence non-critical directives while stationary in pit box or running with pit limiter active.
      - `PhaseOutLap` & `PhaseInLap`: Out-lap focuses strictly on thermal prep, clean air gap spacing, and traffic behind; in-lap focuses on cooldown, battery recharge, and letting flying laps pass.
    - **Audio Queueing, Radio Spacing & Incident Discipline:**
      - Frontend sequential speech queue (`useTTSPlayback.ts`) ensures non-critical directives play sequentially without clipping; critical emergencies (`UrgencyCritical` / `UrgencyHigh`) preempt active speech.
      - Push-to-talk answers are spoken sentence by sentence while they stream (`useRadioAudio.ts` feeds `createSentenceChunker` into `useTTSPlayback.beginReplyStream()`): each sentence's TTS is prefetched, the reply opens and closes with one beep pair, goes ahead of queued non-critical calls, and is dropped by a forced interrupt or a new PTT press, which also aborts the pending request.
      - Global radio spacing enforces a minimum 4-second gap (`GlobalRadioChatterCooldownMs = 4_000`) between non-critical calls across categories.
      - Steward penalties strictly supersede corner cutting warnings on the same event frame.
      - Neutralization shield suppresses sector delta coaching, fuel delta, rival battles, and tyre overheat during SC/VSC or local yellow flags. Sector deltas are capped to `0.35s <= delta <= 3.0s` to prevent incident conflation.
      - Dynamic weather onset (`flags_rain_live`) and tyre compound crossover strategy (`tyre_crossover`) trigger pit box calls upon track grip transitions.
*   **Global Background PTT:** On Windows, native DirectInput listening (`winmm.dll` for steering wheels, `user32.dll` for keyboard) captures PTT globally in the background so radio works while driving F1 in full screen. Browser Gamepad API and `Space` key act as fallback.

## 7. Multi-Language & Localization Standards
*   **English-First Base & Type-Safe I18n:** All underlying codebase structures, backend APIs, default telemetry payloads, and English dictionaries (`frontend/src/locales/en/`) serve as the primary base schema.
*   **Backend Localization Architecture (`internal/locales`):** Eliminates hardcoded boolean language flags (`isEnglish`, `isSpanish`). Provides a type-safe `PromptCatalog` interface with English base fallback (`EnglishCatalog`), authentic Latin American motorsport Spanish catalog (`SpanishCatalog`), thread-safe registry (`Resolve`, `Get`), and unified Microsoft Edge Neural TTS voice mappings.
*   **Multi-Language UI Support:** The frontend includes native, zero-dependency type-safe internationalization via `I18nProvider` and `useI18n` (`frontend/src/context/I18nContext.tsx`). Supported locales:
    - `en`: **English** (default) with 🇬🇧 flag indicator.
    - `es`: **Español (Latinoamérica)** with 🇦🇷 Argentina flag indicator (`"Español (Latinoamérica)"`), utilizing authentic Latin American motorsport terminology (*boxes*, *neumáticos*, *monoplaza*, *vuelta rápida*, *diferencia*). Standard international F1 acronyms (*DRS*, *ERS*, *S1/S2/S3*, *SC/VSC*, *RPM*, tyre compound letters) remain universally recognizable across all languages.
*   **Language Selector UI:** Compact glassmorphic dropdown (`frontend/src/components/LanguageSelector.tsx`) integrated in the top navigation bar right next to the port status badge. Preference automatically syncs with browser settings and persists in `localStorage` (`f1_telemetry_language`).

## 8. Clean Code, Constants & Engineering Principles
*   **Zero Magic Numbers / Literals Policy:** Never use hardcoded, unexplained numeric literals or inline raw status codes across the Go backend or React frontend (e.g. raw packet IDs `1`, `2`, `3`, `6`, `7`, `10`, `16`; result statuses `0..7`; safety car modes `0..3`; weather types `0..5`; tyre compound numbers `16..21`; time conversion constants like `60000`, `1000`, `3600000`; ERS store capacities `4000000.0`; buffer capacities `1800`; downsampling thresholds `800`/`850`; default colors).
*   **Go Backend Constants Location:** All F1 protocol enums, result statuses, pit statuses, driver statuses, safety car modes, weather codes, actual tyre compound IDs, and standard conversions MUST reside in `internal/packets/constants.go` or dedicated domain-specific constant files (`constants_drivers.go`, `constants_teams.go`, `constants_sessions.go`) and be referenced as `packets.ResultStatusFinished`, `packets.PitStatusPitting`, `packets.MillisPerMinute`, `packets.MaxERSStoreEnergyJoules`, `packets.DefaultTelemetrySampleCapacity`, `packets.DriverName(...)`, `packets.TeamName(...)`, `packets.SessionTypeName(...)`, etc.
*   **React Frontend Constants Location:** All frontend F1 constants, packet IDs, compound IDs, penalty types, session types, time constants, and UI downsample thresholds MUST reside in `frontend/src/constants/f1.ts` (e.g. `PACKET_IDS`, `RESULT_STATUS`, `PIT_STATUS`, `DRIVER_STATUS`, `SAFETY_CAR_STATUS`, `PENALTY_TYPES`, `WEATHER_CODES`, `SESSION_TYPES`, `TIME_CONSTANTS`, `TELEMETRY_DOWNSAMPLE_LIMITS`, `ACTIVE_AERO_MODES`) and be imported directly across components and hooks.
*   **Core Engineering Principles:**
    - **DRY (Don't Repeat Yourself):** Always reuse centralized constants, shared Go types, TypeScript interfaces, conversion helpers, and custom hooks instead of duplicating parsing logic, unit conversions, or calculation math across packages or components.
    - **Single Responsibility & Separation of Concerns:** Keep HTTP handlers thin (transport and validation only); computational analytics, session state, and strategy rules belong in dedicated service layers (`internal/analytics`, `internal/session`, `internal/engineer`); React components focus strictly on presentation with telemetry state managed via Zustand.
    - **KISS (Keep It Simple, Stupid) & YAGNI:** Prioritize clean, straightforward, and testable code over premature abstractions, speculative generalized interfaces, or unnecessary configuration overhead.
