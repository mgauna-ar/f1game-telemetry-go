# F1 Game Telemetry Project Rules

This file (`.agents/AGENTS.md`) contains workspace-specific rules, architectural boundaries, and operational constraints that agents must strictly follow when working on this project.

## 1. Technology Stack & Architecture
*   **Supported OS:** Windows 10/11, macOS, and Linux (cross-platform).
*   **Target Telemetry Version:** Exclusive target for **F1 2025** and **F1 2026 DLC** UDP telemetry specifications (`PacketFormat` 2025/2026 with fixed 29-byte `PacketHeader`). Deprecated support for 2023 and older formats.
*   **Backend Layer Boundaries (Go):** Standard Go layout (`cmd/` and `internal/`).
    - `internal/api/`: HTTP router, request decoding, middleware, and response serialization only. **Zero heavy domain or analytical logic.**
    - `internal/session/`: Live session tracking, `LapTracker` memory buffering, `TelemetryBatchWriter`, and session import/export services.
    - `internal/analytics/`: Server-side computational analytics (classification standings, lap comparator distance merging, progression matrices, tyre stint degradation OLS regression).
    - `internal/engineer/`: Modular Strategy pattern AI race engineer rules engine (`EngineerEngine`, `EngineerRule`). The engine also keeps the race history (player laps, rival session histories, race events, its own radio calls) and builds the live race picture the AI chat reads (`RaceContext()`, `LiveBriefing()`; served at `GET /api/ai/engineer/race-context`). `internal/ai` reads it through the `ai.LiveRaceSource` interface. `RaceTools()` exposes the race data lookups (`race_tools*.go`) as an `ai.ToolExecutor`.
    - **AI chat context is built on the server:** `POST /api/ai/chat` carries only identifiers in `context` (`ai.ChatContextRequest`: `context_mode` from `ai.ChatContextModes`, plus `session_id` for `session_debrief`, or `lap_a_id`, `lap_b_id` and an optional `zoom` range for `comparator`). `ai.BuildChatContext` builds the prompt data before streaming starts: the live briefing from `ai.LiveRaceSource` (none while telemetry is stale, so the prompt stands by), and the debrief and lap comparison from `ai.RecordedRaceSource`, which `analytics.ChatContextSource` implements (`BuildSessionDebrief` from the classification, `BuildLapComparison` from the merge the Lap Comparator charts use, through the shared `MergeLapComparisonCached`). The API layer adds the saved voice settings' call-sign and custom persona; an unknown session or lap is a 404 and a bad context a 400, both with code `INVALID_REQUEST`. The driving phase, 2026 rules and incident status come only from the engine's briefing, never from text. The browser never writes prompt text or summaries.
    - `internal/storage/`: SQLite repository, data models with custom `MarshalJSON` sanitization, versioned migrations, and raw zstd compression.
    - `internal/packets/`: Strict 1:1 binary UDP telemetry decoders and domain constants.
    - `internal/ai/`: External AI providers (Gemini, OpenAI, Anthropic Claude, and OpenAI-compatible "custom" servers) and neural TTS voice synthesis. `provider.go` is the provider registry: each provider's default model (`DefaultModel()`), which server key it uses (`ServerKeys`), and how to list its models and open a chat. Each provider lives in one file (`gemini.go`, `openai.go`, `claude.go`) and implements `chatSession`: stream one model turn, then append tool results. `chat.go` runs the one shared function calling loop over the `ToolExecutor` in `ChatOptions`: at most `MaxToolRounds` rounds, the last one with function calls disabled, and a retry without tools when a model or OpenAI-compatible server rejects them. Text streams to the client as it arrives in any round, and the stream ends with a single `[DONE]`. Claude goes through the official Go SDK (`github.com/anthropics/anthropic-sdk-go`) with environment defaults off, so it only uses the key the app resolved; Gemini and OpenAI use plain HTTP (`http.go`, `sse.go`). API keys go in headers, never in URLs, and the "custom" provider only uses a key sent with the request.
    - `internal/locales/`: Type-safe `PromptCatalog` interface, thread-safe locale registry, and locale-specific prompt catalogs (`en`, `es`) eliminating boolean language flags in the backend.
    - `internal/input/`: DirectInput PTT wheel and keyboard OS listeners.
*   **Storage Invariants:**
    - CGO-free pure Go SQLite (`modernc.org/sqlite`) with versioned migrations (`schema_version` table).
    - Per-lap telemetry samples buffered in memory and persisted as Zstandard (`zstd`) compressed JSON BLOBs (`lap_telemetry` table) with cascading foreign keys (`ON DELETE CASCADE`).
    - **Settings ownership:** Settings every device shares live in `internal/settings` (one JSON document each in the `settings` table) behind `GET`/`PUT /api/settings/{ai,voice,ptt,engineer}` (`settings.Sections`): AI provider, model and API keys per provider (keys are write-only and never returned), the engineer's persona and voice, push-to-talk (applied to the input manager at startup), and the race engineer setup. **The race engineer setup** (`settings.Engineer`, stored under `engineer_config`) holds only what the radio settings panel picks: the driver's `engineer.Tuning` (radio spacing and thresholds), the trigger preset and the panel's `alert_switches` (keys from `engineer.AlertSwitchKeys`, which tsc checks `ALERT_TOGGLE_KEYS` against through the generated `EngineerAlertSwitch` union). It is loaded on top of `settings.DefaultEngineer()` so new fields keep their defaults, and a setup saved before the switches were stored is migrated on load. The server builds what the engine runs (`Engineer.EngineConfig()`): the engine's `EnabledCategories` come from `engineer.EnabledCategoriesFromSwitches` (the one table that lists which engine keys, aliases included, each switch turns off; a missing switch counts as on), and the global radio spacing, critical wing damage and qualifying time warning always come from `engineer.DefaultEngineerConfig()`. The browser never sends enabled categories or server constants. The UI reads defaults from `GET /api/settings/engineer/defaults` instead of hard-coding them. Every engineer save carries the `version` it was based on; the server bumps it, and a save based on an older version gets `409` with code `SETTINGS_CONFLICT`, after which the dashboard reloads the saved setup and shows a notice. A PUT decodes on top of the saved setup, so omitted fields keep their value. After any successful settings PUT the server sends `settings_changed` (`api.SettingsChangedMessage`: `section`, the saving tab's `X-Dashboard-Client` id as `source`, and the engineer `version`) on `/ws/engineer`. The dashboard saves settings only through `putSettings(section, body)` (`frontend/src/utils/settingsClient.ts`, which sends this tab's `DASHBOARD_CLIENT_ID`) and listens with `subscribeSettingsChanges(section, …)`, which skips the tab's own saves: `components/common/SettingsSync.tsx` reloads the engineer and voice settings (not while a save of its own is pending, nor for an engineer version it already has), and `useAISettings` and `usePTTConfig` reload theirs. Race engineer saves are debounced with one request in flight; every `syncConfigToBackend()` promise resolves once the save that includes its change finishes, and a change made during a save is sent right after it with the new version. Failed saves go to `useSettingsSaveStore` (`reportSettingsSaveFailure`), and `SettingsSync` shows them as toasts; never swallow a settings save error. AI requests are completed in the API layer in the order request, saved setting, env var (`GEMINI_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `LLM_PROVIDER`, `LLM_MODEL`), built-in default, and `internal/ai` owns the default model names. Only per-device preferences (volume, radio effects, alerts on/off, view modes, the AI chat's expanded size) live in `localStorage`, through `frontend/src/utils/storage.ts`, with every key listed in its `KnownStorageKey` type. The router rejects cross-site writes (`http.CrossOriginProtection`) and sends no CORS headers. The WebSocket upgrader keeps gorilla's default origin check, so `/ws` and `/ws/engineer` only accept handshakes whose `Origin` host equals the request `Host` (the dashboard by localhost or LAN address, or the Vite dev proxy) or that send no `Origin` (non-browser clients); never override `CheckOrigin`. JSON request bodies on `/api` are capped at `MaxJSONBodyBytes` (2 MB); `POST /api/sessions/import` sits outside that group with its own `MaxImportPayloadSize` (100 MB). The update check always queries `system.DefaultGitHubRepo`. Server startup settings come from flags, then environment variables, then an optional `.env` file.
    - **Session UIDs must always be stored and serialized as Hex strings** (`TEXT` e.g. `0x...`) to prevent 64-bit signed integer overflow and JavaScript float truncation.
*   **Single-Binary Release & Frontend Distribution:** Compiled Vite frontend (`frontend/dist`) is embedded directly into the Go executable via `//go:embed` (`frontend/embed.go`), serving static assets with SPA fallback and automatic browser launch (`system.OpenBrowser`). Produces a 100% self-contained binary with zero external runtime dependencies.
*   **Communication & Performance:** `/ws` carries one message type: the throttled 10Hz consolidated Live Telemetry Snapshot (`PacketIDLiveSnapshot` 255), and the frontend store ignores anything else. The snapshot is a slim DTO (`session.LiveSnapshot` in `internal/session/live_snapshot.go`), not the raw packets: one row per active car (`ActiveCarCount`, which keeps a retired car's slot), only the packet fields the live views read (same PascalCase names and types as the packet structs), only the filled weather forecast samples, and no marshal zones. The store copies the rows as they are. The engineer engine and session recording keep reading the raw packets. `TestLiveSnapshotPayloadSize` (`cmd/simulator`, run with `-v`) measures a simulator frame against the raw packet snapshot for both formats. **The server owns the race-control feed:** `LiveBroadcaster` turns the game's events (Packet ID 3) and the rows it builds from session and lap data (pit entry, penalty counter, retirement, DSQ, safety car) into one `session.FeedEvent` shape (`internal/session/feed_events.go`: an event code from `FeedEventCodes`, a feed type and severity, and typed parameters such as vehicle indices, driver names, penalty type and time, lap, speed and safety-car status; never text, and an unnamed car gets no name), queues them, and sends them in the next snapshot's `Events`. The store only appends them (`useSessionStatusStore.addEvent`); `frontend/src/utils/raceEvents.ts` writes every row's text and tag in `en` and `es`, with a switch `tsc` checks against the generated `FeedEventCode` union. Both sockets are ref-counted singletons built on `createSharedSocket(path)` in `frontend/src/utils/websocketClient.ts` (`connectTelemetryWebSocket`, and `subscribeEngineerMessages` in `frontend/src/utils/engineerSocket.ts`): the first subscriber's URL wins, and handler exceptions are logged with `console.error`. `/ws/engineer` consumers never cast frames: they pass one handler per message type to `subscribeEngineerMessages`, and `dispatchEngineerMessage` drops anything that isn't a known `EngineerSocketMessage` type. On the Go side the API layer sends its messages only through `Server.broadcastEngineer`, which takes the typed PTT and `settings_changed` messages; the engine broadcasts its `EngineerDirective`s itself. React frontend uses decoupled Zustand stores (`useTelemetryStore`) with fine-grained selectors to eliminate unnecessary whole-page re-renders. The AI race engineer context is split in three (`context/RaceEngineerContextDefinitions.ts`): `useRaceEngineerActions()` holds only callbacks that never change identity (`useAIChatStream` and `useAIModels` read the latest messages, settings and chat target through refs), `useRaceEngineerState()` holds the chat window, context mode, chat targets (`ComparatorChatTarget`, `SessionDebriefChatTarget`: IDs plus a track name for the badge) and AI settings (the provider derives the mode and targets from the URL with `chatTargetsFromRoute`; pages never set them), and `useRaceEngineerStream()` the messages. The app shell and the pages only use the actions, so nothing re-renders on a timer or per streamed chunk (`App.rerender.test.tsx`); `utils/chatContext.ts` turns the mode and targets into the request's `context`. Streaming SSE for AI Race Engineer (`/api/ai/chat`) follows one contract on both sides: the server (`internal/ai/sse.go`) sends `data: {"text":…}` chunks and a final `data: [DONE]`; a provider failure after streaming starts is sent as one last `data: {"error","code","provider","message"}` frame on the 200 response (built by `aiErrorPayload` in `internal/api/ai.go`), and a request rejected before streaming gets a non-OK JSON response with the same fields (bad request bodies use code `INVALID_REQUEST`). The frontend reads it only through `frontend/src/utils/sseUtils.ts`: `readChatStream(res, onText)` (reads `text`, does not require `[DONE]`, throws a typed `ChatStreamError` with the server's `code` on an error frame) and `chatStreamErrorFromResponse(res)` for non-OK responses; both the chat panel (`useAIChatStream`) and push-to-talk radio (`useRadioAudio`) use them. Error codes come from the server (`classifyAIError` in `internal/ai/errors.go`); the client only labels requests that never got an answer as `NETWORK_ERROR`. Model lists from `POST /api/ai/models` are already filtered to chat models by the server. Chat replies and release notes are parsed by `frontend/src/utils/markdown.ts` (headings, nested lists, tables, code, quotes; unfinished blocks stay text while streaming) and rendered as React elements by `components/ui/Markdown.tsx`, never as raw HTML; it is the app's only markdown renderer. The AI settings panel (`ChatSettingsDrawer`) shows one card per provider and only that provider's fields; OpenAI-compatible server presets live in `AI_SERVER_PRESETS` (`constants/f1.ts`).
*   **Wire Types (Go → TypeScript):** The frontend's types for server JSON are generated from the Go structs by `cmd/tsgen` into `frontend/src/types/generated/` (one file per Go package; never edit them, never hand-copy a wire type). `cmd/tsgen/main.go` is the registry of root types: the REST responses (sessions and the session list items with their summaries, laps, participants, tags, the session detail with its classification, progression and stints, comparator, import, settings (including the race engineer setup and its `EngineerAlertSwitch` union), system, AI models and errors), the AI chat request (`ai.AIChatRequest`, with the `ChatContextMode` union built from `ai.ChatContextModes`), the `/ws/engineer` messages (`EngineerSocketMessage` = `EngineerDirective` | `PTTEventMessage` | `PTTLearnedMessage` | `PTTLearnTimeoutMessage` | `SettingsChangedMessage`, with its `SettingsSection` union built from `settings.Sections`, with the directive's `EngineerAlertKey`, `EngineerDirectiveCategory` and `EngineerUrgency` unions built from `engineer.RadioAlertKeys`, `DirectiveCategories` and `Urgencies`) and the race feed (`session.FeedEvent`, plus the `FeedEventCode`, `FeedEventType` and `FeedSeverity` unions built from the Go lists in `internal/session/feed_events.go`). The generator (`internal/tsgen`, standard library only) follows the `encoding/json` rules; a field whose JSON differs from its Go type carries a `tstype:"…"` tag, rows of a `[]map[string]any` are described with `TypeAlias`, and a type with its own `MarshalJSON` must be registered with `Marshaler` (a sample value plus the type describing its JSON; `TestMarshalerKeys` checks one against the other). Responses are named structs, never `map[string]any`. Hand-written files re-export the generated types (`types/session.ts`, `types/settings.ts`, `types/telemetry.ts`, …); where the UI narrows a Go `string` to a union it uses `Narrows<T, Base>` (`types/wire.ts`), so `tsc` still checks it against Go. Tests build complete wire objects with the factories in `frontend/src/test/wireFactories.ts`. The 10 Hz live snapshot is registered as `session.LiveSnapshot`; `types/telemetry.ts` re-exports its rows under the names the components use (`LapData`, `CarStatusData`, `CarDamageData`, `CarTelemetryData`, `CarTelemetry2Data`, `ParticipantData`, and `SessionData` = `LiveSession` plus the header's `PacketFormat` and `SessionUID`), and tests build them with the `makeLive*` factories.
*   **REST Errors:** Non-OK REST responses carry `{"error","code"}` (`internal/api/response.go`). The frontend calls REST only through `frontend/src/utils/apiClient.ts`: every method (JSON, form data, blob, array buffer) goes through one `request()`, and `parseErrorResponse()` turns the body's `error` text into `ApiError.message`, which toasts show as is; `api.stream()` alone returns the raw `Response` for `sseUtils.ts`. A failed `POST /api/sessions/import` (400) sends the import summary with `error` set to the first `details[].reason`. Batch export is `POST /api/sessions/export-batch` with a JSON `{"session_ids":[…]}` body only.
*   **Session Detail & Session Data Cache:** Session History opens a session with one request, `GET /api/sessions/{id}/detail` (`analytics.SessionDetailResponse`, built by `analytics.ComputeSessionDetail` from one load of the session, participants and laps). Participants and laps are sent once, at the top level; `DriverStanding` and `DriverStint` never embed laps or participants (their Go fields that do are `json:"-"`), and the client joins them by `car_index` and `best_lap_id` in `normalizeDriverStanding` (`types/session.ts`). The participants and laps of a session go through `frontend/src/utils/sessionDataCache.ts`: `useSessionDetail` primes it, and the comparator (`useSlotTelemetry`) reads it with `getSessionLapData`, which shares one `/participants` + `/laps` load per session between both slots and keeps at most `SESSION_DATA_CACHE_LIMIT` sessions. Deleting sessions drops them from the cache and importing clears it. `TestSessionViewPayloadSize` (`internal/api`, run with `-v`) checks that a session view sends each lap once and reads the database once (session, participants, laps and events), and prints the bytes and event rows.
*   **Stored Race-Control Events & the Story Tab:** The race-control feed is built once, by `LiveBroadcaster` (`internal/session/feed_events.go`); every 100 ms tick hands the new rows to its `FeedEventSink`, with or without dashboards connected, and `cmd/server` points the sink at `SessionManager.RecordFeedEvents`, which stamps each row with the leader's lap (`FeedEvent.RaceLap`, from the P1 car's lap data) and saves it to `session_events` (migration 7: `session_id`, `lap`, `session_time`, `event_code`, `data` = the row's JSON; rows of a session that is no longer current are dropped). `storage.SessionEvent` rows travel in exports (`ExportedSessionPackage.Events`) and imports, and `session.StoredFeedEvents` decodes them for `SessionDetailResponse.Events`. `analytics.RaceControlPeriods` reads the SC/VSC periods from the SCAR rows (a status change closes the open period; formation laps are ignored), and `BuildSessionDebrief(session, cls, events)` adds a "RACE CONTROL KEY MOMENTS" section (periods, red flags, retirements, DSQs, time/drive-through/stop-go/grid penalties, the player's collisions and overtakes made and suffered). **In the dashboard,** the detail tabs are `story | classification | pace | position | gap | stints | sectors` (`SESSION_DETAIL_TABS`; `/history/:id` is the story, the old `/charts` opens `pace`; `RACE_CHART_TABS` are for races only). `utils/raceStory.ts` has the client rules: `raceControlPeriods` (same as the server), `keyMoments` (the story's rows: other cars' overtakes, pit stops and speed traps are left out, only the last fastest lap is kept; overtakes and collisions are yours from either side, anything else only when `vehicleIdx` is yours), `momentsByLap`, and `fieldPace` (your clean lap times against the field median and fastest; a lap needs clean times from a third of the field and at least 3 cars, and SC/VSC laps are left out of the average). `session_history/story/` holds `SessionStoryTab` (`YourRaceCard`, `FieldPaceChart`, `SessionDebriefPanel`, and `KeyMomentsTimeline` beside them above laptop width), and `raceControlAreas` draws the SC/VSC shading in the lap charts. `SessionDebriefPanel` runs its own `useAIChatStream` with the `session_debrief` context and only on a click; finished debriefs are kept per session for the page's lifetime. `SessionLapChartsTab` takes a `chart` prop and, from `SessionDetailView`, the selected drivers, so the pace, position and gap tabs share them.
*   **Stint Degradation Fits:** `ComputeSessionStints(session, participants, laps, periods)` (periods from `RaceControlPeriods(events)`; nil for sessions without stored events) fits each stint's slope (`CalculateDegradationSlope`, at least 3 laps) and `avg_lap_time_ms` on its clean laps only; `best_lap_time_ms` is still the best of every lap. `stintExclusions` leaves out, in this order, the in and out laps (`analyzeDriverLapOutliers` on the driver's whole race), the laps inside an SC/VSC period (`neutralisedLaps`, in leader laps, an open period running to the last lap, a full SC winning over the VSC on a shared lap), and then the laps `analyzeDriverLapOutliers` finds over 107% of the median of the stint's remaining laps. `DriverStint` carries `fit_laps` and `excluded_laps` (`StintExcludedLap`: `lap_number`, `reason` = `pit_in` | `pit_out` | `sc` | `vsc` | `slow`); in `degradation_data` a left-out lap's time sits under `{key}_excluded` with `{key}_reason` instead of `{key}`. **In the dashboard,** `stints/DegradationTable.tsx` lists every stint (sortable by driver, tyre, rate, laps used, clean average, best; no rate always sorts last) with a checkbox per stint; `SessionStintStrategyTab` keeps the selection per stint key (`stintKey`, `stintKeysOf`; at first every stint of `defaultChartSelection`), and a driver button in the timeline toggles all that driver's stints. `DegradationCurves` charts only the ticked stints, draws left-out laps as hollow dots, and caps the y-range at 107% of the median charted lap so a lap or stint under an unstored safety car doesn't flatten the curves.
*   **Session List Views, Filters & the Classification Gap:** `utils/sessionListView.ts` holds the list's pure rules: `QuickFilter` (`recent` = last `RECENT_DAYS`, `yours`, `podium`, `gained`, all from `summary.player`) and `matchQuickFilter`, `groupSessions` (by day (newest first unless the list is sorted by date ascending), track or tag (a session under each of its tags, untagged last), keeping the list's sort inside each group), `pageGroups`, and `SavedSessionFilter` with `normalizeSavedFilters`/`isSameFilter`. `useSessionFilters` applies the quick filters with the others; `useSessionListPreferences` keeps the grouping (`f1_history_group_by`) and up to `MAX_SAVED_FILTERS` saved filters (`f1_history_saved_filters`) per browser; the provider exposes `quickFilters`, `groupBy`, `savedFilters`, `toggleQuickFilter`, `setGroupBy`, `saveCurrentFilter`, `applySavedFilter` (drops a deleted tag), `deleteSavedFilter` and `resetFilters`. `SessionQuickBar` (in the filter toolbar) shows them. `useSessionListPaging` groups and pages the list (`SESSION_PAGE_SIZE` = 50, "Show more" in `SessionListMore`) and folds groups; the page and folds start over when the list or grouping changes. `SessionTableView` renders groups through `DataTable`'s `groups` prop (one `<tbody>` per group under a `<th scope="rowgroup">` heading, `SessionGroupHeading`) and passes the same paging to `SessionCardList`, whose group headings are `h2` and card titles `h3`. Export, tags and delete are in `SessionActionsMenu`, built on `ui/Menu` (menu button pattern, rendered in a portal at fixed coordinates, closes on scroll, outside click, Esc and Tab); the explore button is named "Explore: <track>". In a session, `ClassificationTable` has a Gap/Interval `SegmentedControl`: `timeGapText` takes the car ahead (the row above) and, in interval mode, gives the time to it or the laps it leads by; the leader and cars out of the race read the same in both modes. `SectorTime` takes `isSlower` (yellow, `data-best="none"`) for completed sectors that aren't a best, used in the classification and a driver's laps; the sector leaderboard only marks the session best purple. `getTrackInfo` matches an exact name or alias before a partial one (bare "Spa" used to resolve to Spain).
*   **The Player's Car & Session List Summaries:** `sessions.player_car_index` (migration 6, `storage.Session.PlayerCarIndex`, `number | null`) is the car the player drove, set by `SessionManager.handleNewSession` from `PacketHeader.PlayerCarIndex` (null when it is not a grid car, as while spectating). Sessions recorded before the migration are not backfilled and stay null; the UI finds the player in those by the comparator's saved driver name (`f1_comparator_default_driver_name`). `GET /api/sessions` returns `analytics.SessionListItem` (the session's own JSON plus `summary`: `leader`, `fastest_lap`, `laps_completed` and `player`), computed by `analytics.ComputeSessionList` from the same classification as the detail view, with every listed session's participants and laps loaded in two queries (`storage.Repository.GetSessionResults`). `analytics.FindPlayerStanding` is the one lookup of the player's standing: the stored car, else (only when a `?driver=` name is given) the first car whose name contains it or whose race number equals it, as `findParticipantByPartialName` matches in the comparator; `player.source` (`PlayerSource`: `recorded` | `driver_name`) says which. `BuildSessionDebrief` writes the player's result first, marks their line `(YOU)` and lists them and the cars either side even outside the top `DebriefMaxDrivers`, only for a stored player car. **In the dashboard,** `useSessionListStore` holds `SessionListItem[]` and sends `?driver=` with `savedDriverName()` (`utils/comparatorPreferencesUtils.ts`; saving a new name in the comparator refetches the list). `utils/player.ts` is the client's one player lookup: `findPlayer(participants, player_car_index, savedName)` (same rule as the server) and `defaultChartSelection`/`defaultChartCars` (the player and two cars either side, else the top 5). `useSessionDetail` exposes `playerCarIndex`/`playerSource` through the history context; the classification table marks that row (`tr.you` plus a YOU badge), `YourRaceCard` sums it up, and the progression and degradation charts start from it with a YOU chip. The list shows `YourResult` in the table and in `SessionCardList`, and a session's format badge only when it differs from the list's usual one (`commonPacketFormat`). The comparator's default laps go through `resolveReferenceLap(…, playerCarIndex)` and `resolveComparisonLap(…, referencePlayerCarIndex)`, and its slots wait for the session list before loading, so the choice never races the list. Before any lap is picked, the comparator offers quick-start comparisons built from the list summaries (`utils/comparatorQuickStart.ts`: your best lap against the session's fastest or, when yours was the fastest, the next fastest that slot B picks; against your best the previous time at that track; at another track). Its "Where did I lose time" table (`lap_comparator/CornerTable.tsx`) comes from `analyzeCorners` in `utils/trackTurns.ts`: each detected turn gets the stretch from halfway to the previous apex to halfway to the next (capped at `CORNER_APPROACH_MAX_METERS` before and `CORNER_EXIT_MAX_METERS` after), with both laps' entry and minimum speed, braking point, throttle pickup and the time delta across it; a row sets the URL's zoom (charts and `ComparatorTrackMap`'s `zoomRange`), and "Ask AI" writes that zoom to the URL before `openChat` sends its question, so the chat context carries the corner. The timing tower opens while a lap is missing and folds once both laps are picked. The charts come as cards or as strips (`f1_comparator_chart_view`): `lap_comparator/charts/StripCharts.tsx` draws one Recharts strip per trace from `charts/stripTraces.ts` (`STRIP_TRACES`: data keys, domain, value and axis formats) on one `syncId`, shows the values under the cursor beside each strip instead of tooltips, zooms on a drag of at least `MIN_DRAG_ZOOM_METERS` (`dragZoomRange`), and keeps the strip order and hidden strips per device (`f1_comparator_strip_layout`, read through `normalizeStripLayout`, so traces added later still appear). **Progress** (`/progress[/:track]`, `components/progress/`): `GET /api/progress?track=&driver=` returns `analytics.TrackProgressResponse` (built by `ComputeTrackProgress` from `GetSessions` and `GetSessionResults` for that track's sessions only): the track list (`ProgressTracks`, latest first), one `ProgressSession` per session where `FindPlayerStanding` finds the player (oldest first: best lap and best valid sectors from the classification, the session's fastest lap and `gap_to_fastest_ms`, `consistency_ms` as the standard deviation of `cleanLapTimes` from `MinConsistencyLaps` of them), and `unmatched_sessions`. Clean laps are the pace chart's (`analyzeDriverLapOutliers`: no in or out lap, none over 107% of the median) that are valid and not a race's lap 1. The page (`useTrackProgress`, which sends `savedDriverName()`) computes the personal best, best sectors and theoretical best client-side (`progressStats.ts`) and filters by session kind; below phone width the sessions table becomes cards.
*   **URL routing:** The dashboard has no router dependency: `frontend/src/router/` is a small layer over the History API. `routes.ts` is the one list of pages and their URLs (`parseRoute`, `buildPath`): `/history`, `/history/:sessionId[/:tab]` (the tab is left out for the classification), `/compare?sa=&a=&sb=&b=&zoom=` (sessions and laps of slots A and B, `sb` only when it differs from `sa`, zoom in meters as `from-to`), `/progress[/:track]` (the track percent-encoded; the latest session's track when left out) and `/live/:mode` (`dashboard` or `cockpit`). `/` reopens the last page, `/live` the last live mode, and an unknown path shows the session list; `App` replaces any URL with its canonical form. Read the page with `useRoute()`, change it with `navigate(url, { replace })` or the `Link` component (plain clicks stay in the app, modified and middle clicks open a new tab). A new page or session adds a history entry; changes within a page (a detail tab, the comparator's laps and zoom, the live mode) replace it. The comparator and progress nav tabs go back to the last URL shown on that page. The URL is the source of truth: History shows the session it names, the comparator starts from it and writes its laps and zoom back once the laps asked for have loaded, and the AI chat reads its targets from it. Every page URL is served `index.html` by the Go SPA fallback (`setupStaticRoutes` in `internal/api/server.go`). A new page adds its route to `routes.ts` and its test, and to `TestHandleEmbeddedFrontendAndSPAFallback`.
*   **Live Status & Telemetry Endpoint in the UI:** Only the Live tab opens the telemetry WebSocket. The live feed state (offline / listening / live / stale, stale after 3s without packets) comes from `useLiveStatus()` and drives the nav badge, the live header and the tab title; never show "LIVE" just because the backend is reachable. The UDP port and this PC's addresses come from `GET /api/system/network` (`system.DescribeTelemetryEndpoint`, loaded into `useTelemetryEndpointStore`); never hard-code port 20777 in the UI.

## 3. F1 Telemetry & Radio Protocols
*   **Binary Parsing Alignment:** When modifying packet decoding logic (e.g. `PacketLapData`, `PacketMotionData`), ensure strict 1:1 alignment with official EA F1 2025/2026 game telemetry specification. **Critical gotcha:** `LapDistance` and `TotalDistance` are floats positioned immediately before `SafetyCarDelta`.
*   **Lightweight Payloads:** Keep frontend payloads lightweight — broadcast only the specific data points needed by the UI (e.g. extracting `WorldPositionX/Z` for track maps) rather than sending raw, unparsed packets. A live view that needs another packet field adds it to the matching `Live*` struct in `internal/session/live_snapshot.go` (and its `toLive*` converter), then regenerates the wire types; never send a whole packet struct.
*   **Proactive Radio Protocol:**
    - **The dashboard owns the spoken wording of proactive calls.** A directive on `/ws/engineer` carries its alert key (`sub_alert`, one of `engineer.RadioAlertKeys`), category and urgency, and no text; `Title` and `Message` stay on the server for the log and the AI race history. The dashboard maps the key to a phrase category (`frontend/src/constants/radioAlertCategories.ts`, a `Record<EngineerAlertKey, RadioAlertCategory>` that `tsc` checks) and speaks a random phrase for the persona from `locales/{en,es}/radio_phrases.ts` (`getProactiveRadioSpeech`; Bono and Colapinto fall back to the standard pool, custom always uses it). Never guess a category from text, and never read the engine's text out. A new alert needs its key in `RadioAlertKeys` (`TestRadioAlertKeys_MatchWhatTheEngineEmits` checks it against the rules), a category in `radioAlertCategories.ts`, and phrases in both catalogs; F1 2026 variants are their own keys (e.g. `rival_attack_override`).
    - All proactive pit wall alerts are prefixed with `[PROACTIVE PIT WALL CALL]`.
    - **Explicitly forbid "Entendido" / "Copy" / "Roger" on proactive calls** since the engineer initiates the communication.
    - "Entendido" / "Copy" / "Roger" are **only** permitted when the driver spoke first via Push-to-Talk (PTT).
    - **Direct 2nd Person Radio Voice:** Directives must instruct the driver directly in 2nd person (e.g., *"Box now, box box!"*, *"Introduce Lift & Coast into Turn 1"*), never 3rd person directives (*"Order driver to..."*).
    - **Phase Lifecycle Discipline:** Strict radio discipline per session phase (`DrivingPhase`):
      - `PhaseFlyingLap`: Strictly silence non-critical coaching, fuel delta, ERS low, tyre wear, and rival chatter. Only lap invalidations and critical emergencies (`UrgencyCritical`) may transmit.
      - `PhaseGrid` & `PhaseRaceStart`: Absolute radio silence during countdown and Lap 1 start sequence, permitting only critical safety car or terminal damage calls.
      - `PhaseInGarage` & `PhasePitLane`: Only strategic session alerts (clock countdown, radar, red flags) adapted for garage/pit lane; no driving coaching or on-track tyre alerts. Silence non-critical directives while stationary in pit box or running with pit limiter active.
      - `PhaseOutLap` & `PhaseInLap`: Out-lap focuses strictly on thermal prep, clean air gap spacing, and traffic behind; in-lap focuses on cooldown, battery recharge, and letting flying laps pass.
    - **Audio Queueing, Radio Spacing & Incident Discipline:**
      - Frontend sequential speech queue (`useTTSPlayback.ts`) ensures non-critical directives play sequentially without clipping; critical emergencies (`UrgencyCritical` / `UrgencyHigh`) preempt active speech.
      - Push-to-talk answers are spoken sentence by sentence while they stream (`useRadioAudio.ts` feeds `createSentenceChunker` into `useTTSPlayback.beginReplyStream()`): each sentence's TTS is prefetched, the reply opens and closes with one beep pair, goes ahead of queued non-critical calls, and is dropped by a forced interrupt or a new PTT press, which also aborts the pending request.
      - Global radio spacing enforces a minimum 4-second gap (`GlobalRadioChatterCooldownMs = 4_000`) between non-critical calls across categories.
      - Steward penalties strictly supersede corner cutting warnings on the same event frame.
      - Neutralization shield suppresses sector delta coaching, fuel delta, rival battles, and tyre overheat during SC/VSC or local yellow flags. Sector deltas are capped to `0.35s <= delta <= 3.0s` to prevent incident conflation.
      - Dynamic weather onset (`flags_rain_live`) and tyre compound crossover strategy (`tyre_crossover`) trigger pit box calls upon track grip transitions.
*   **Global Background PTT:** On Windows, native DirectInput listening (`winmm.dll` for steering wheels, `user32.dll` for keyboard) captures PTT globally in the background so radio works while driving F1 in full screen. Browser Gamepad API and `Space` key act as fallback.

## 4. UI/UX Guidelines
*   **Design Aesthetic:** Build modern, responsive React components. Use curated color palettes, smooth micro-animations for real-time data updates, and avoid default browser styling to maintain a premium feel.
*   **Design Tokens:** `frontend/src/styles/base/variables.css` is the one source for colours, spacing, type, radius, shadows, layers and motion: surfaces (`--bg-*`), text (`--text-primary` > `--text-body` > `--text-secondary` > `--text-muted`, each at least 4.5:1 on every surface; `--text-muted` is the floor), borders, brand accents (`--accent-*`, with `--accent-cyan` for radio, AI and live highlights), status (`--status-success|warning|danger|info` plus `-bg`/`-border` tints), F1 colours (`--f1-slot-a|b`, sector regions `--f1-sector-1|2|3`, timing `--f1-purple|green|yellow`, compounds `--f1-compound-*`, `--f1-gold`, `--f1-team-fallback`), weather (`--weather-*`), charts (`--chart-*`), and the `--space-*`, `--font-size-*`, `--radius-*`, `--shadow-*`, `--z-*` and `--duration-*`/`--ease-*` scales. Components use `var(--token)`, never a new colour literal. TypeScript reads tokens only through `frontend/src/styles/theme.ts`: `cssVar(token)` for inline styles and Recharts SVG props (the browser resolves it), `getCssVars({...})` for canvas palettes (read once per draw, since canvas can't resolve `var()`), `alpha(color, amount)` for tints of a token or hex colour (never append a hex alpha such as `${color}40`), `canvasRgba` for translucent canvas colours, and `styleVars({ '--team-color': color })` to hand a data-driven value to a CSS Module as a custom property. `THEME_TOKENS` lists every token TypeScript may read, so `cssVar` with an unknown token fails `tsc`, and `theme.test.ts` checks that `variables.css` defines each one. Compound colours come from `TYRE_COMPOUNDS` through `getVisualCompoundId`, team colours from `getTeamColor(teamId)` (both in `constants/f1.ts`), and comparator chart colours from `CHART_COLORS` (`lap_comparator/charts/chartDefaults.ts`). Anything stacked above the page uses a `--z-*` layer: nav < docks < popovers < dialogs < toasts < tooltips.
*   **Accessibility:** `frontend/src/styles/base/accessibility.css` is global: one `:focus-visible` ring (a component recolours it with `--focus-ring-color`; only text fields that draw their own focus state may set `outline: none`), `.sr-only` text, and a `prefers-reduced-motion` block that finishes every CSS animation and transition at once; JavaScript animation (canvas loops, smooth scrolling) checks `prefersReducedMotion()` (`utils/motion.ts`). Anything clickable is a `<button>` (add the global `.button-reset` class to make one look like its content) or a link, with its state in `aria-pressed`, `aria-expanded`, `aria-selected` or `aria-current`; a clickable row, card or backdrop may keep its click only as a shortcut for a real button that does the same, marked `role="presentation"`. Sortable tables put `aria-sort` on the `<th>` and a button inside it. Colour is never the only cue: purple and green sector times render through `components/common/SectorTime.tsx` (a corner notch, a tooltip and screen-reader text). Toasts live in a region that is always mounted (`aria-live="polite"`, errors `role="alert"`). `npm run lint` enforces the interaction rules with oxlint's `jsx-a11y` plugin (`frontend/.oxlintrc.json`).
*   **Shared UI components:** `frontend/src/components/ui/` holds the building blocks, each with its own CSS Module (`Name.module.css`): `Button`/`IconButton` (defaults to `type="button"`; an icon button's `label` is its name and tooltip), `Modal` with `ModalHeader`/`ModalBody`/`ModalDescription`/`ModalFooter`, `Panel`/`PanelHeader` (a glass card named by its title), `Badge`, `Tabs`/`TabPanel` (WAI-ARIA tabs with arrow keys), `SegmentedControl` (a radio group for view modes and filters), `DataTable` (caption, `aria-sort` and sort buttons, row headers, numeric columns, `renderExpanded` for a full-width row such as a driver's laps), `Stat` (with an optional `detail` line), `Switch` (on/off, a native checkbox with `role="switch"`), `Slider` (range input), `TextInput`/`TextArea`/`Select` (`Field.tsx`), `EmptyState` (also for errors, announced), `Skeleton`/`SkeletonGroup`/`SkeletonRows` (loading, announced), `Tooltip`/`useTooltip`, and `Markdown`. Use them instead of new one-off markup. Every modal dialog is a `Modal` (portal, `aria-modal`, Tab kept inside, Esc and backdrop close, focus back to the opener, first focus on the first control after the close button). Panels that leave the page usable, like the AI chat and its settings layer, use `useDialogLayer` (`components/ui/useDialogLayer.ts`) without the Tab trap: Esc closes only the newest open layer, and an Esc a control inside already handled (`preventDefault`) is left alone, as a tooltip does. Class names join with `cx` (`components/ui/cx.ts`). Base styles (tokens, reset, typography, glass, focus ring, reduced motion, and the `mono`, `sr-only`, `glass-panel`, `button-reset` and `animate-spin` helpers) stay global in `styles/base/`; every other stylesheet is a CSS Module next to its component (`Name.module.css`, camelCase classes). **Breakpoints** are three names from `styles/breakpoints.ts`: `@media (--phone)` (≤600px), `(--tablet)` (≤900px) and `(--laptop)` (≤1100px). The `breakpointMedia` PostCSS plugin in `vite.config.ts` expands them in every stylesheet, composed ones included, and fails the build on an unknown name; `breakpoints.test.ts` rejects a raw `max-width`/`min-width` media query. Components read the same widths with `useMediaQuery(maxWidth('tablet'))` (`hooks/useMediaQuery.ts`, false in tests unless `matchMedia` is stubbed), as the session list does to switch from the table to `SessionCardList` below a tablet's width. A component whose layout depends on its own width rather than the window's (the AI chat's reading mode, the live `SessionHeader`, the top nav's short tab names) declares a named size container and uses `@container` queries. The floating docks share `--dock-inset`, `--launcher-size`, `--floating-dock-clearance` and `--session-dock-clearance` (`variables.css`): on tablets and phones the AI launcher is a round icon, the radio pill ends before it, and the history docks sit above it; `main` keeps the clearance free, more while a `[data-session-dock]` is showing. Pages on the 12-column grid pull in `styles/pageGrid.module.css` with `composes` and tune it through its custom properties. In a module, colours and sizes are tokens; only data-driven values (a team or tag colour, a bar width, a popover position) stay inline, preferably as a custom property through `styleVars`. A module may restyle a `ui` component by passing `className` (its rules load after the component's own); state lives in attributes (`aria-pressed`, `aria-checked`, `data-*`) that the module selects on, not in extra class names. Vitest processes `*.module.css` with their written class names (`test.css` in `vite.config.ts`), so prefer roles, labels and `data-*` attributes (such as `Badge`'s `data-tone`) over class names in tests.

## 8. Clean Code, Constants & Engineering Principles
*   **Zero Magic Numbers / Literals Policy:** Never use hardcoded, unexplained numeric literals or inline raw status codes across the Go backend or React frontend (e.g. raw packet IDs `1`, `2`, `3`, `6`, `7`, `10`, `16`; result statuses `0..7`; safety car modes `0..3`; weather types `0..5`; tyre compound numbers `16..21`; time conversion constants like `60000`, `1000`, `3600000`; ERS store capacities `4000000.0`; buffer capacities `1800`; downsampling thresholds `800`/`850`; default colors).
*   **Go Backend Constants Location:** All F1 protocol enums, result statuses, pit statuses, driver statuses, safety car modes, weather codes, actual tyre compound IDs, and standard conversions MUST reside in `internal/packets/constants.go` or dedicated domain-specific constant files (`constants_drivers.go`, `constants_teams.go`, `constants_sessions.go`) and be referenced as `packets.ResultStatusFinished`, `packets.PitStatusPitting`, `packets.MillisPerMinute`, `packets.MaxERSStoreEnergyJoules`, `packets.DefaultTelemetrySampleCapacity`, `packets.DriverName(...)`, `packets.TeamName(...)`, `packets.SessionTypeName(...)`, etc.
*   **React Frontend Constants Location:** All frontend F1 constants, packet IDs, compound IDs, penalty types, session types, time constants, and UI downsample thresholds MUST reside in `frontend/src/constants/f1.ts` (e.g. `PACKET_IDS`, `RESULT_STATUS`, `PIT_STATUS`, `DRIVER_STATUS`, `SAFETY_CAR_STATUS`, `PENALTY_TYPES`, `WEATHER_CODES`, `SESSION_TYPES`, `TIME_CONSTANTS`, `TELEMETRY_DOWNSAMPLE_LIMITS`, `ACTIVE_AERO_MODES`) and be imported directly across components and hooks.
*   **Core Engineering Principles:**
    - **DRY (Don't Repeat Yourself):** Always reuse centralized constants, shared Go types, TypeScript interfaces, conversion helpers, and custom hooks instead of duplicating parsing logic, unit conversions, or calculation math across packages or components.
    - **Single Responsibility & Separation of Concerns:** Keep HTTP handlers thin (transport and validation only); computational analytics, session state, and strategy rules belong in dedicated service layers (`internal/analytics`, `internal/session`, `internal/engineer`); React components focus strictly on presentation with telemetry state managed via Zustand.
    - **KISS (Keep It Simple, Stupid) & YAGNI:** Prioritize clean, straightforward, and testable code over premature abstractions, speculative generalized interfaces, or unnecessary configuration overhead.
